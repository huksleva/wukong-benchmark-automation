# Защита Wukong Benchmark Automation

[← README](../README.md) · [Архитектура](ARCHITECTURE.md) · [Методика](PROFILES.md) · [Проверка](VALIDATION.md)

## Что показать за 3–5 минут

1. **Задача.** «Я разработал локальную утилиту на C#, которая сама запускает бесплатный Black Myth: Wukong Benchmark Tool из Steam, применяет два профиля, читает результаты самого инструмента и сохраняет отчёт».
2. **Сценарий.** «После проверки установки и OCR программа резервирует настройки, запускает CPU-проход, затем GPU-проход, закрывает свои процессы и восстанавливает исходные INI. Начальную подсказку и меню проходит автоматически. Первоначальные соглашения и вход в Steam остаются за пользователем».
3. **Настройки.** «CPU: 1280×720, TSR 50%, Low и High для дальности. Это снижает работу GPU. GPU: 1920×1080, TSR 100%, Cinematic; трассировка на максимуме, если доступна. Генерация кадров, VSync и лимит FPS отключены. Профили фиксированы для воспроизводимости».
4. **Доказательство.** Откройте [настоящий отчёт](results/2026-10-08/report.html) вместе с исходными экранами и настройками. «На Ryzen 5 5560U с Radeon Graphics оба прохода выполнены автоматически: CPU — 27/22/32 FPS, GPU — 2/2/2. RT недоступна, что отражено в отчёте. Это сохранённый замер 8 октября 2026 года».
5. **Надёжность и границы.** «FPS не вычисляются внешним счётчиком: я распознаю итоговый экран, проверяю числа и подтверждаю их несколькими кадрами. Настройки повторно проверяются после Apply. Есть тайм-ауты, отмена и частичный отчёт. Полный игровой сценарий проверен на одном Windows-компьютере; CI проверяет код и пакеты, но не запускает игру».

Для демонстрации без ожидания игровых проходов достаточно сохранённого отчёта. Не представляйте его как новый замер компьютера, на котором проходит защита. Для живого запуска используйте готовый EXE и заранее подготовьте Steam, OCR, соглашения и шейдеры; не взаимодействуйте с компьютером во время проходов. Путь запуска приведён в [README](../README.md#быстрый-старт).

## Соответствие заданию

| Требование | Реализация и подтверждение | Граница подтверждения |
|---|---|---|
| Инструмент на C# для локального Steam Benchmark Tool | Windows-приложение; обнаружение Steam и AppID 3132990 | Бесплатный Benchmark Tool устанавливается отдельно |
| Два последовательных автоматических прохода | Оркестратор `Program.RunAsync`, оба результата в настоящем отчёте | После первоначальной подготовки, на одном проверенном компьютере |
| Настройки с минимальным влиянием GPU для CPU-теста | CPU-профиль, проверка значений в UI, контрольные PNG | Фактический CPU-упор не доказан: загрузка GPU не измеряется; слабая GPU может ограничивать даже этот профиль |
| Высокая GPU-нагрузка | Full HD, Cinematic, TSR 100%, максимально доступная RT | Это тяжёлый фиксированный профиль, а не гарантия максимальной загрузки на любой GPU; RT имеет явный fallback |
| Дождаться завершения и автоматически разобрать результаты | Итоговый экран, стабильные кадры, Windows OCR и цифровой Tesseract | Меню другой версии и неизвестные подписи могут потребовать обновления адаптера |
| Вывести CPU, GPU, RAM, результаты и настройки обоих тестов | CIM-данные, HTML/JSON и исходные артефакты | Фактическая загрузка компонентов в отчёт не входит |
| Доступное решение, инструкция и обоснование | GitHub, Releases, README, PROFILES | Linux/macOS-приложение читает отчёты; новые игровые тесты выполняет Windows |

**Оценка готовности:** основной функциональный сценарий реализован и подтверждён настоящим автоматическим запуском. Строгую изоляцию CPU/GPU нельзя объявлять выполненной только по названию пресета. Для такого утверждения нужна дополнительная проверка загрузки компонентов и зависимости FPS от разрешения. Эта методологическая граница — главный пункт, который стоит озвучить самостоятельно.

## Как устроен проект

```text
Windows: проверка установки и OCR → резервная копия INI
         → CPU: запуск → настройка → тест → OCR → закрытие
         → GPU: запуск → настройка → тест → OCR → закрытие
         → восстановление INI → HTML + JSON + консоль

Core:    модели, INI, парсер FPS, генератор отчёта
Engine:  общий сценарий меню и интерфейсы окон/OCR
Windows: Steam, Win32, Windows OCR, Tesseract, CIM
Reports: чтение сохранённых JSON на Linux/macOS/Windows
```

Оркестратор управляет порядком шагов. `UiAutomation` распознаёт состояние экрана и проверяет настройки; `NativeWindow` реализует ввод и захват конкретного игрового окна. `SettingsBackup` хранит исходные INI побайтово. `ResultParser` извлекает метрики, а `ReportWriter.Write` сериализует JSON и создаёт HTML через `StringBuilder`, экранируя строки `WebUtility.HtmlEncode`. Отчёт работает локально и не требует сервера или внешних JavaScript-библиотек.

## Вероятные вопросы

**Почему не изменить всё через INI?** Известные стандартные параметры применяются через INI, но они не гарантируют, что конкретная сборка игры применила настройки. Остальные значения задаются в меню; после Apply проводится повторное чтение UI. В отчёте запрос через INI отличается от подтверждения в интерфейсе.

**Почему автоматизация не состоит из кликов по фиксированным координатам?** Координаты действий обычно берутся из OCR-геометрии распознанной подписи и значения. При этом есть относительные области меню и сводки, адаптированные к проверенной сборке; универсальная независимость от любой вёрстки не заявляется.

**Зачем два OCR?** Windows OCR читает подписи, значения и русские/английские меню. Крупные стилизованные цифры среднего FPS читаются локальным Tesseract при двух порогах контраста; чтения должны совпасть. Неоднозначный результат не выдаётся за успешный.

**Чем 95% FPS above отличается от 1% low?** Это показатель самого Benchmark Tool: порог, выше которого находится 95% измеренных FPS. Он не называется 1% low и не пересчитывается в другую метрику. Если он не прочитан, сохраняется `null`; распознанное значение должно попадать между min и max.

**Почему GPU дал 2 FPS — это ошибка?** Это число на исходном итоговом экране при тяжёлом профиле на интегрированной графике. Инструмент предупреждает о низкой VRAM. Низкий FPS является результатом измерения, а не поводом подменить его более красивым числом.

**Почему CPU не Full HD?** Меньшее разрешение и 50% внутреннего масштаба снижают стоимость обработки пикселей на GPU. Сохранена высокая дальность сцены. Это намерение профиля; фактический ограничитель нужно подтвердить измерениями.

**Почему GPU Full HD, а не 4K?** Full HD — фиксированная точка сравнения для проверенного сценария. 4K может сильнее нагрузить GPU, но не доступно на каждом дисплее. Разрешение настраивается явно; результаты другого протокола сравниваются отдельно.

**Можно ли двигать мышью или переключать окна?** Ввод и рабочий стол общие. Есть предупреждение, задержка и попытки фокусировки, но блокировки ввода и автоматического признания замера недействительным нет. Вмешательство может испортить сценарий или условия замера; такой тест следует повторить.

**Что произойдёт при ошибке?** При неизвестном экране или неверной обязательной настройке сценарий прекращается. В основной секции завершения закрываются процессы Benchmark Tool из выбранной установки, восстанавливаются INI, сохраняются статус и ошибка. `Ctrl+C` проходит через эту же очистку. При завершении процесса через диспетчер задач или отключении питания восстановление не гарантировано; резервная копия остаётся для ручного восстановления.

**Что, если Steam или игра отсутствуют?** Мастер предлагает открыть установку и повторить проверку. Неполная установка выявляется до изменения настроек. Полная платная игра не требуется; соглашения и авторизацию программа за пользователя не принимает.

**Что, если браузер отсутствует?** Успех замера сохраняется. Метрики и пути HTML/JSON печатаются в консоли; отчёт можно открыть позже. Chrome не является зависимостью.

**Работает ли на Linux/macOS?** Нативное приложение Reports собирается и тестируется на Linux x64/ARM64 и macOS Intel/Apple Silicon. Оно читает сохранённые результаты. Полный игровой Windows-адаптер на эти ОС не перенесён; наличие переносимого Engine не равно готовому игровому порту.

**Почему нет Docker?** Контейнер не решает задачу управления видимым Windows-окном и запуска Steam-игры с GPU на всех трёх ОС. Для этого проекта проще и честнее автономный Windows EXE и нативный Reports. Docker удалён из проекта.

**Что доказывает GitHub Actions?** Сборку, регрессионные проверки, упаковку и работу CLI на указанных ОС. Steam, игровые проходы и FPS CI не проверяет. Источник подтверждения игровых проходов — опубликованные исходные PNG и сведения о реальном запуске.

**Что вы намеренно не усложняли?** Не добавлял сервер, базу данных и облачные OCR для локальной задачи. Рабочую последовательность меню сохранил; дополнительные адаптеры отделены интерфейсами. Оптимизация больших систем хранения здесь не нужна.

## Последняя проверка и дальнейшая работа

Финальный аудит исправил обработку `null` в пользовательских настройках, пустого пути результатов, нечисловой позиции колонки и противоречивого дополнительного FPS. Регрессии сначала воспроизведены, затем исправлены. Локально выполнены 43 проверки Windows, 5 проверок Engine и 12 проверок CLI Reports, включая повторную проверку распакованного пакета. Два реальных CPU/GPU-прохода после этих ограниченных изменений повторно не выполнялись; исходные артефакты прошлого запуска сохранены без изменений. Текущие задания сборки доступны в [Actions](https://github.com/huksleva/wukong-benchmark-automation/actions/workflows/build.yml).

Для приближения к продакшену приоритеты следующие: восстановление после аварийного завершения; матрица настоящих игровых проверок на разных GPU и Windows; обнаружение вмешательства и признание замера недействительным; прогрев и повторения с оценкой разброса; телеметрия загрузки для проверки CPU/GPU-упора; подпись EXE и управляемое обновление зависимостей. Полный игровой Linux/macOS-порт требует отдельных адаптеров и настоящих проходов на этих ОС.
